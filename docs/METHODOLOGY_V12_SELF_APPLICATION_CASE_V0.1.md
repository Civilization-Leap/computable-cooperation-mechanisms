# Methodology V1.2 Self-Application Case V0.1

## Purpose

This document applies the methodology in **From Theory to Reality V1.2** back to the **Computable Competition–Cooperation Mechanisms (CCM)** project itself.

It is a **maintainer-side self-application**, not independent validation of the methodology and not proof that CCM has already solved real-world competition/cooperation problems.

The purpose is narrower:

1. test whether the V1.2 method can describe a live project without forcing success claims;
2. distinguish direct problem-solving evidence from infrastructure, reproduction, and diffusion evidence;
3. expose what evidence is still missing before CCM can claim real-world use, accumulation, or wider civilizational contribution.

---

## 1. Project startup card

### Real problem

Competition and cooperation decisions are often made with interests, constraints, third-party burdens, unknowns, and irreversible consequences only partially visible. Existing discussions can collapse into positions, slogans, or single-objective optimization.

CCM explores whether a small open reference implementation can make part of that structure more explicit and challengeable.

### Subject goals

Different users may bring different goals. CCM does not require them to adopt a single optimization objective. The current project goal is to help users compare declared arrangements without silently collapsing actor-specific effects, hard constraints, and unknowns into one score.

### Theory increment

The project adds an explicit distinction between:

- cooperation and non-cooperation consequences;
- actor-specific ordinary gains and losses;
- third-party burdens;
- declared hard constraints;
- explicit UNKNOWN values;
- precise rule execution and rule legitimacy.

The threshold-sensitivity case is especially important: identical outcome deltas can produce different verdicts when only the declared protection line changes. This demonstrates that computation can enforce a line without establishing who had the right to draw it.

### Direct purpose

The direct purpose is **not** “build software” or “obtain adoption.” It is to help real users reason more clearly about a concrete competition/cooperation problem and improve an actual decision, negotiation, arrangement, or risk judgment.

**Current evidence status:** this direct purpose has **not yet been demonstrated through a documented external real-world case** in the public repository.

### Purpose of the purpose

If repeated use leaves better judgment capabilities with participants, produces reusable solution structures, spreads across independent actors, and continues to pass the civilization-direction gate, those accumulated changes may contribute to better default ways of handling competition and cooperation.

No such higher-order outcome is claimed here.

## 2. Current method and tool state

The public repository currently provides:

- a v0.1.1 reference evaluator;
- actor/dimension/unit separated outcomes;
- baseline/candidate deltas;
- independent hard-constraint checks;
- explicit UNKNOWN preservation;
- strict rejection of unsupported fields and undeclared units;
- deterministic output with reproducibility hash and interpretation boundary;
- optional CI exit gates for VIOLATED and UNKNOWN;
- synthetic teaching examples;
- BYOP problem intake, capability ledger, mapping guidance, feedback protocol, domain templates, and draft forms;
- third-party testing guidance and an independent implementation challenge.

This is a **small reference implementation**, not a universal decision engine, fairness certifier, behavioral predictor, or real-world authorization system.

This distinction is deliberate and should be preserved.

## 4. Reality-layer evidence card

### Baseline

Before the project, the relevant problem class often lacked a small, open, deterministic reference tool explicitly separating ordinary gains, hard constraints, third-party burdens, and unknowns.

### Intervention

CCM introduced a public reference implementation plus guides, synthetic cases, testing paths, BYOP intake, and reusable domain templates.

### Observable results currently supported

- the tool is runnable locally;
- the current suite is exercised in CI across Python 3.11–3.13;
- v0.1.1 provides explicit semantic exit codes;
- v0.1.0 has a Zenodo archive and DOI;
- the repository records one user-reported successful reproduction of the frozen v0.1.0 materials on Python 3.12.3;
- the repository distinguishes that report from independent verification of v0.1.1.

### What is not yet supported

- no public evidence yet establishes that CCM materially improved a live negotiation, policy choice, business arrangement, or institutional decision;
- no public evidence yet establishes durable user capability retention;
- no public evidence yet establishes independent cross-actor reuse at scale;
- no public evidence yet establishes rule, institutional, or default-behavior change.

## 5. Civilization accumulation assessment

### A. Capability retention

**Current status: UNKNOWN / NOT YET EVIDENCED EXTERNALLY**

The project teaches reusable questions, for example:

- who benefits and who bears the burden;
- what happens under cooperation and non-cooperation;
- who is affected but absent from the table;
- what remains unknown;
- what hard boundaries cannot be offset by ordinary gains;
- what evidence would change the initial judgment.

However, the public repository does not yet contain external evidence showing that an independent user retained and later reused this judgment structure without maintainer assistance.

### B. Solution reuse

**Current status: EARLY / PARTIAL**

Reusable acquisition and platform-rule-change templates exist. They show that repeated structures can be extracted from cases without expanding the core prematurely.

External independent reuse is not yet established.

### C. Cross-actor diffusion

**Current status: NOT YET DEMONSTRATED**

The repository is public, Apache-2.0 licensed, and designed for forks and independent implementations. Availability is not the same as adoption. No broad cross-actor diffusion claim is made.

### D. Direction consistency

**Current status: PASS FOR CURRENT PUBLIC DESIGN BOUNDARIES; REAL-WORLD EFFECTS REMAIN PARTLY UNKNOWN**

The current public design supports the direction gate in several ways:

- actor-specific burdens remain visible;
- hard constraints are checked separately from ordinary gains;
- UNKNOWN is preserved rather than silently filled;
- the tool does not certify fairness or legitimacy;
- computation is explicitly separated from authorization;
- independent challenge, counterexample, and fork paths are encouraged.

Remaining UNKNOWNs include how downstream users may adapt the tool, whether a domain fork could be used for asymmetric pressure, and whether real institutional deployment would preserve the same safeguards.

---

## 6. Direction gate

The current public reference implementation passes the **pre-template / pre-propagation direction gate** at the level of its declared design, because it makes burdens and constraints visible, preserves unknowns, and rejects the claim that precise computation itself creates legitimacy.

This is **not** a permanent certification.

The gate must be re-run when:

- a new reusable template is created;
- a domain extension is promoted;
- a downstream implementation materially changes semantics;
- new evidence indicates asymmetric exploitation, burden hiding, or loss of exit/correction space.

Any future VETO finding should block active promotion of that solution path even if it is efficient or locally successful.

---

## 7. Feedback classification for this self-application

### H — Accumulation Evidence / Decay

Needed next:

- evidence that independent users retain the problem-framing capability;
- evidence of repeated use without maintainer guidance;
- evidence of template reuse across separate cases;
- evidence of continued use or later abandonment.

### I — Direction Deviation / Misuse

Watch for:

- use of declared vulnerability boundaries as optimization targets against weaker actors;
- reporting only local gains while suppressing third-party burdens;
- downstream claims that a SATISFIED result proves legitimacy or fairness;
- removal of UNKNOWN or interpretation boundaries to produce false certainty.

---

## 8. Upgrade and downgrade discipline

Current project claims should remain at their actual evidence level.

Examples:

- “publicly runnable” may be claimed;
- “CI-tested across supported Python versions” may be claimed for the current repository state;
- “user-reported v0.1.0 reproduction exists” may be claimed with scope;
- “independently validated v0.1.1” should **not** be claimed without new evidence;
- “solves real-world competition/cooperation problems” should **not** be claimed yet;
- “contributes to civilization transition” should **not** be claimed as an achieved result.

If a previously reported adoption, reuse, or effectiveness claim later proves weaker than believed, the state should be downgraded with the original claim, date, triggering evidence, and new state preserved.

---

## 9. What this self-application reveals about Methodology V1.2

The V1.2 method successfully prevents a common inflation error: treating infrastructure completion as purpose achievement.

Applied to CCM, it forces a clear separation between:

- theory articulated;
- method documented;
- software runnable;
- tests passing;
- public access available;
- external reproduction reported;
- real-world problem solved;
- capability retained;
- solution independently reused;
- wider institutional or civilizational accumulation.

These are not interchangeable evidence states.

The strongest result of this first self-application is therefore not a success claim. It is a **boundary claim**:

> CCM has built a public, reproducible, challengeable starting point and a real-use intake loop. The next evidence frontier is no longer “can the repository run?” but “can an independent real-world user solve or materially improve a real problem, retain the method, and leave evidence that another actor can reuse it?”

---

## 10. Next evidence milestone

The next methodology milestone should be one **external, non-sensitive, reversible real-world case** that can be documented end to end:

1. user-defined purpose;
2. baseline;
3. at least two real alternatives;
4. affected third parties;
5. hard boundaries and UNKNOWNs;
6. current-tool fit and representation gaps;
7. actual decision or negotiation change;
8. result after a defined time window;
9. whether the user can repeat the method without maintainer help;
10. whether any part of the solution is reused by another independent actor.

Only after such evidence exists should the project move its status from infrastructure-level readiness toward demonstrated domain use.
