## 1. Case positioning

The main value of this self-application is not a success claim. It is a boundary claim: infrastructure completion must not be promoted into purpose achievement.

CCM currently has public theory, documentation, a runnable evaluator, tests, BYOP intake, domain templates, release/archival material, and challenge paths. Those are distinct from evidence that an external real-world problem was actually improved.

---

## 2. Startup card

### Real problem

Competition/cooperation decisions often hide actor-specific burdens, third-party effects, unknowns, hard constraints, exit conditions, and irreversible consequences.

### Subject goals

Users may bring different goals. CCM does not impose one universal optimization objective.

### Theory increment

CCM separates ordinary gains/losses, hard constraints, third-party burdens, explicit UNKNOWN, and precise rule execution from rule legitimacy.

### Direct purpose

Help a real user reason more clearly about a concrete competition/cooperation problem and materially improve a decision, negotiation, arrangement, or risk judgment.

**Current status: NOT YET DEMONSTRATED through an external real-world case.**

### Purpose of the purpose

Repeated real use may contribute to civilization accumulation only if capability is retained, solutions are reused, diffusion is independently evidenced, and the direction gate continues to pass.

### Stop / pause conditions

Pause computation, active promotion, or status upgrading when any of the following occurs:

- a key direction-gate item is VETO;
- a key direction-gate item is UNKNOWN and promotion would create material irreversible exposure;
- known third-party burdens are omitted from a downstream presentation;
- declared vulnerability boundaries are repurposed as optimization targets against the affected actor;
- evidence supporting an adoption/effectiveness claim is withdrawn or contradicted;
- the problem cannot be represented without material distortion;
- a high-consequence use would require assumptions beyond current evidence.

## 6. Anti-misuse / reverse-use defense review

This check runs at the same two gate times and again for every new domain layer.

| Check | CCM current state | Result / action |
|---|---|---|
| Local-gain clipping | full reports retain actor-specific deltas and hard checks | PASS; downstream clipping is I-class deviation |
| Vulnerability converted to optimization target | core does not expose an optimizer, but declared limits could still be read adversarially | UNKNOWN; do not describe boundaries as bargaining targets |
| Permission/provenance | evaluator does not establish who is authorized to use or disclose inputs | UNKNOWN; deployment must add permissions/data governance |
| Irreversibility amplification | reference cases are synthetic; live downstream use unknown | UNKNOWN; high-consequence deployment pauses pending domain evidence |
| One-sided optimum packaging | tool explicitly refuses fairness/legitimacy certification | PASS at design level |
| Protective action | interpretation boundaries, UNKNOWN, hard-check separation | PARTIAL; domain deployments may require minimization/redaction/access control |

### Atomic-report semantic rule

If a report contains a known third-party burden, hard-constraint violation, or UNKNOWN relevant to interpretation, that context is part of the declared semantic report. A downstream presentation that extracts only local gains while hiding those known burdens is classified as **I — Direction Deviation / Misuse**.

This is a semantic governance rule, not a claim that the current file format cryptographically prevents downstream copying or truncation.

## 8. Diffusion resistance is evidence, not merely an obstacle

A solution that meets resistance should not automatically trigger a strategy for overcoming that resistance. Resistance may reveal hidden costs, power asymmetries, legal constraints, or burden shifts the method failed to represent.

Persistent resistance from actors who bear consequences is therefore treated as an evidence signal:

- first classify the objection using A–I;
- if it indicates hidden burden, exclusion, or direction deviation, trigger direction-gate review;
- only after the objection is represented and the gate remains open should sandboxing, parallel running, reversible pilots, compatibility layers, or standardization be considered.

---

## 9. Direct-purpose evidence milestone is staged to avoid evidence deadlock

### Milestone A — real-problem closure

Goal: obtain one external, non-sensitive, reversible live case.

Minimum evidence:

1. user-defined purpose;
2. baseline;
3. at least two genuine alternatives;
4. affected third parties;
5. hard boundaries and UNKNOWNs;
6. tool fit / representation gaps;
7. documented decision or negotiation change;
8. decision-maker confirmation that the comparison exposed a material constraint, burden, or alternative relevant to the actual decision.

If this evidence is credible, Stage 9 may move from NOT DEMONSTRATED toward **DOMAIN USE (single-case scope)**. This does not establish capability retention or civilization accumulation.

### Milestone B — accumulation follow-up

After a suitable follow-up window, collect H-class evidence:

- did the user reuse the method without maintainer assistance?
- did another independent actor reuse the template or solution structure?
- was the use sustained, abandoned, or reversed?
- did any I-class deviation emerge?

Milestone B is deliberately separate from Milestone A so real-problem evidence is not blocked by higher-order accumulation evidence.

## 10. Reproduction-count discipline

A single reproduction report and stable repeatability are not equivalent.

Any reproduction evidence record should include:

- software/release version;
- environment;
- reproducing party;
- date;
- number of successful repetitions if known;
- whether the maintainer independently re-ran the same package;
- whether the run is independent execution or only user-reported;
- scope limitations.

The currently documented v0.1.0 reproduction remains one user-reported run within its stated scope. It is not promoted into stable independent reproducibility of v0.1.1.

## 11. External challenge box

External challenge is explicitly invited.

If a reviewer can construct an input, downstream use, or semantic argument showing that CCM hides a known burden, turns a vulnerability boundary into an exploitation target, or makes a legitimacy claim unsupported by its semantics, submit:

- **B — Counterexample**, when the current model/assumption fails; or
- **I — Direction Deviation / Misuse**, when the method or output is used in a direction inconsistent with the declared boundary.

Challenge entry points:

- public BYOP / feedback issues in this repository;
- third-party testing and counterexample channels already linked from the README.

A substantiated challenge can trigger status freeze, downgrade, template withdrawal, or direction-gate re-review. No endorsement is requested.
