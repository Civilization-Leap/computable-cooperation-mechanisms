# Reusable Domain Template | Platform Rule Change / Multi-Actor Burden

**Status:** experimental reusable template candidate

Use this template when a platform, marketplace, app ecosystem, creator economy, payment system, or other intermediary changes rules that redistribute benefits, costs, access, risk, or control across multiple actor classes.

## 1. Typical rule changes

- fee or commission changes
- ranking or recommendation changes
- access or steering rules
- payment or settlement rules
- API or interoperability restrictions
- content or moderation rules
- eligibility or participation requirements
- security or compliance requirements

## 2. Required actor map

Identify separately where relevant:

- platform / rule setter
- business users, developers, sellers, creators, or service providers
- end users / consumers
- payment, distribution, or infrastructure intermediaries
- competitors or alternative channels
- regulators or public authorities
- third parties who may bear indirect effects

A rule setter and an affected actor must not be collapsed into one generic actor.

## 3. Actor purposes

State each actor's own purpose. Typical examples include platform security, revenue, ecosystem stability, market access, lower fees, user choice, convenience, privacy, competition, or regulatory compliance.

## 4. Baseline and candidates

Define the current rule set as the baseline. Compare separate candidate rule sets, for example:

1. current centralized rule;
2. wider external steering or alternative purchase access;
3. third-party distribution or alternative channel access with explicit safeguards;
4. revised fee / compliance structure;
5. status quo where the proposed change is not adopted.

## 5. Dimensions to keep separate

Possible dimensions include:

- fees / revenue
- access / discoverability
- user price
- user choice
- security burden
- compliance cost
- switching cost
- dependency on the platform
- dispute / appeal access
- data access or portability
- third-party exposure
- exit or alternative-channel availability

Do not create a single fairness score merely to rank candidates.

## 6. Hard boundaries

Examples may include minimum access, maximum declared burden, required appeal path, minimum interoperability, security constraints, privacy constraints, or other non-offsettable conditions.

For every boundary, record who set it, the source, who is affected, and whether legitimacy is contested.

## 7. What v0.1.1 can do

- compare declared static outcome changes for multiple actor classes;
- check declared hard constraints;
- preserve UNKNOWN;
- expose when one actor gains while another bears a declared cost;
- compare multiple static rule candidates against one baseline.

## 8. What remains outside the current core

Do not silently encode:

- real security probabilities;
- dynamic ecosystem adaptation;
- market-power evolution;
- strategic retaliation;
- algorithmic ranking behavior;
- legal interpretation;
- actual user consent;
- institutional legitimacy;
- real-world authorization.

These remain evidence limits, representation gaps, or domain-extension needs.

## 9. Interpretation rule

A valid result means only: under these declared inputs and declared rules, these actor-specific changes and constraint results follow.

It does not mean the platform rule is lawful, fair, efficient, legitimate, or should be adopted.

## 10. Feedback classes

Likely classes include C MISSING ACTOR / IMPACT, A REPRESENTATION GAP, D MISSING CONSTRAINT, E MISINTERPRETATION RISK, and F DOMAIN EXTENSION.

Repeated problems should first produce reusable rule-change templates before any core/schema expansion.

## 11. Recommended BYOP questions

- Who sets the rule?
- Who can comply, refuse, exit, or appeal?
- Who gains from the change?
- Who bears direct and indirect costs?
- Which actor is missing from the negotiating table?
- Which burdens cannot be offset by aggregate gains?
- What remains unknown?
- What changes if the rule is not adopted?
